Smplrspace 与 Archilogic 对比：从数字平面图到空间数据系统

介绍并对比 Smplrspace 和 Archilogic 两个空间数据与数字平面图平台，从产品定位、开发者能力、数据模型、适用场景和选型角度分析差异。

最近在看空间数据、楼宇数字孪生和室内地图相关产品时，两个名字经常会出现：Smplrspace 和 Archilogic。它们都能把静态平面图变成可交互的数字空间，也都提供 SDK/API 给软件系统集成使用，但两者的重心并不一样。

一句话概括：

  • Smplrspace 更像一个面向产品集成的数字平面图与 2D/3D 可视化平台。
  • Archilogic 更像一个面向企业资产组合的空间数据系统，也就是把建筑空间变成可查询、可版本化、可集成的系统记录。

如果你的目标只是“把楼层图放进应用里，并在上面展示传感器、工单、房间、设备等数据”，Smplrspace 会更轻、更直接。如果你的目标是“把整个办公室、楼宇、园区、资产组合变成一套长期维护的空间数据底座”，Archilogic 的体系会更完整。

这两个产品容易被放在一起比较，是因为它们都从“平面图”切入。但它们最终想解决的问题不同。Smplrspace 关注如何把空间做成好用的交互界面；Archilogic 关注如何把空间变成组织内部所有系统都能使用的数据源。

Smplrspace：把空间变成可嵌入的 2D/3D 界面#

Smplrspace 的定位很清楚：把静态 floor plan 转换成可交互的数字空间，并且让开发者可以把它嵌进自己的 Web 产品里。

它支持两类嵌入方式：

  • iframe：集成最简单，适合只需要展示平面图的场景。
  • smplr.js / @smplrspace/smplr-loader：适合需要控制渲染、监听事件、添加数据图层、处理点击位置、切换 2D/3D 的场景。

Smplrspace 文档里把它描述为可以让开发者轻松向应用添加数字化、交互式 floor plans。空间可以用 2D 或 3D 查看，也可以叠加 data layers。这一点很关键：它不是单纯的“室内地图图片查看器”，而是一个可以把业务数据挂到空间上的可视化层。

例如，你可以用它做这些东西：

  • 在办公室平面图上显示会议室状态、工位占用、温湿度传感器。
  • 在物业系统里标出报修位置、设备点位、巡检路线。
  • 在地产 BI 报表中按楼层、区域、单元展示指标。
  • 在 SaaS 产品中嵌入一个可交互的建筑视图，而不是自己从零做 3D/Canvas/WebGL 渲染。

Smplrspace 的一个明显优势是开发者体验直接。Space、startViewer、mode: '2d' | '3d'、enablePickingMode、data layer 这些概念都比较接近前端工程师日常理解。你可以把它当成一个“空间组件”放进产品里，再围绕它绑定自己的数据库和业务逻辑。

不过，它也有一个需要注意的地方：Smplrspace 的前端库目前强调通过官方 CDN 和 loader 使用，不建议自行托管 smplr.js。这对很多早期产品不是问题，但如果你的公司对依赖版本锁定、离线部署、私有化环境有严格要求，就需要提前评估。

Archilogic：把建筑空间变成系统记录#

Archilogic 的表述更企业化。官网把它称为 “spatial system of record”，也就是空间的系统记录。它的类比很直接：Salesforce 是客户的系统记录，Workday 是员工的系统记录，Archilogic 想成为空间的系统记录。

这意味着 Archilogic 不只是在页面上显示一张平面图。它的核心是把建筑和楼层转换成标准化的空间数据模型，然后让这些数据被查询、编辑、版本化、同步、分析和集成。

它的模型大致可以这样理解：

  • 一个 building 下有 floors。
  • 一个 floor 下有 layout / spaces。
  • space 可以有用途、面积、容量、资产等属性。
  • 墙、门、窗、房间、桌子、设备等都可以成为可寻址的数据对象。
  • 第三方系统的数据可以作为 custom attributes 进入空间图谱。

Archilogic 的开发者能力也更偏平台型。它提供 Floor Plan SDK 用于在 Web 中渲染和交互楼层图；提供 REST API 管理建筑、楼层、布局、空间和家具资产；提供 GraphQL API 面向整个 portfolio 或单个楼层做复杂查询；还提供 MCP Server 这样的 AI 工具入口。

这套能力适合更复杂的场景：

  • 大型企业要维护几十、几百个办公室和楼层。
  • Workplace / IWMS / CAFM 系统需要统一空间底图。
  • 会议室预订、工位管理、传感器、清洁、安防、设备维护等系统都要引用同一套空间对象。
  • 企业希望把空间数据交给 BI、自动化规则或 AI agent 查询。
  • 需要面积测量、BOMA 合规、版本控制、变更回滚、权限管理。

如果说 Smplrspace 的第一印象是“好嵌入、好展示”，Archilogic 的第一印象就是“可治理、可查询、可规模化维护”。

数据模型差异#

Smplrspace 和 Archilogic 的关键差别不在“谁能显示 3D”，而在数据模型的深度。

Smplrspace 的数据模型更贴近可视化和应用交互。你关心的是某个空间、楼层、房间、家具或设备在哪里，怎么把业务数据映射上去，用户点了哪里，当前显示哪些楼层，某个数据图层怎么渲染。这种模型适合做产品内的空间界面。

Archilogic 的数据模型更贴近企业级数据治理。它强调 Space Graph，把空间抽象成图结构：空间、资产、结构元素、几何关系、用途、面积、容量、属性、关系都可以被查询。它不是只服务一个前端视图，而是服务一组系统。

可以这样判断：

  • 如果空间数据主要用于“展示给用户看”，Smplrspace 的模型通常够用。
  • 如果空间数据要成为“多个系统共同依赖的事实来源”，Archilogic 更符合这个目标。

开发集成对比#

Smplrspace 的集成路径更像常见的前端 SDK：

import { loadSmplrJs } from "@smplrspace/smplr-loader";

const smplr = await loadSmplrJs();
const space = new smplr.Space({
  spaceId: "spc_xxx",
  clientToken: "pub_xxx",
  containerId: "viewer",
});

await space.startViewer({
  mode: "3d",
  allowModeChange: true,
});

它的优势是上手快。你先把 viewer 跑起来，再逐步加入 data layers、picking mode、custom colors 和事件处理。

Archilogic 的集成更像平台 API。Floor Plan SDK 可以渲染楼层图，GraphQL 可以查询空间对象。例如官网展示的思路是：加载一个 scene，然后从资源里找到某类 space，再 zoom 到它。GraphQL 侧则可以按用途、容量、面积等字段查询楼层和空间。

这种方式的优势是系统性强。前端展示只是其中一层，后端、BI、自动化、AI 工具也可以直接使用同一套空间数据。

适用场景#

Smplrspace 更适合：

  • 你正在做一个 SaaS、IoT、物业、能源、设施管理或地产 BI 产品，需要快速嵌入互动式楼层图。
  • 你重视 2D/3D 展示效果，希望把业务数据直接叠加在平面图上。
  • 你的空间规模从单个楼层、单栋楼到中等规模 portfolio，但重点是“可视化和交互”。
  • 你希望由平台提供数字化服务和数据映射服务，减少自己处理 floor plan 的工作。
  • 你的团队主要是 Web 开发，希望用 JavaScript/TypeScript 解决问题。

Archilogic 更适合：

  • 你是大型企业、办公空间管理团队、PropTech 平台或系统集成商。
  • 你要管理大量楼宇、楼层、空间和资产，并且需要统一的数据模型。
  • 你需要和 Microsoft Places、ServiceNow、Slack、IWMS、IoT、BI、AI 工具等系统连接。
  • 你关心版本控制、权限、面积计算、BOMA 合规、空间用途标准化。
  • 你的目标不是做一个空间 UI，而是建立长期可维护的空间数据基础设施。

成本与复杂度#

从工程复杂度看，Smplrspace 通常更轻。它像一个可嵌入的空间可视化模块，适合从小场景试点开始。对创业公司或产品团队来说，这种路径更容易验证价值：先把一个楼层图跑起来，再接业务数据。

Archilogic 的引入成本更高，但上限也更高。它的价值不是只来自一个 floor plan viewer，而是来自整个空间数据底座。当一个组织有大量空间、多个系统、长期维护和审计需求时，标准化模型和系统记录才会产生复利。

所以不要只比较 SDK 谁更好用。更重要的是问：你要买的是一个“空间展示能力”，还是一个“空间数据管理能力”？

怎么选#

如果我是按项目阶段来选，会这样判断：

  1. MVP 或单产品集成：优先看 Smplrspace。它能较快把 floor plan 变成可交互界面，适合验证“空间可视化是否能提升产品体验”。
  2. IoT / 工单 / 资产点位展示：优先看 Smplrspace，尤其是你主要需求是点位映射、数据图层和用户点击位置。
  3. 企业级空间数据中台：优先看 Archilogic。它的 Space Graph、GraphQL、版本控制和集成能力更适合成为底座。
  4. Workplace / IWMS / CAFM / AI-ready building data：优先看 Archilogic。这里真正难的是数据治理和跨系统一致性，不只是渲染。
  5. 对私有化、版本锁定、合规有强要求：需要重点评估两家的部署、认证、数据边界和合同条款。Archilogic 在企业合规叙事上更完整，Smplrspace 则需要结合具体商业方案确认。

总结#

Smplrspace 和 Archilogic 都在解决“建筑空间如何数字化”的问题，但切入层级不同。

Smplrspace 的强项是把空间做成可嵌入、可交互、可叠加数据的 2D/3D 体验。它适合产品团队快速把楼层图变成业务界面。

Archilogic 的强项是把空间做成标准化、可查询、可版本化、可集成的系统记录。它适合企业和平台团队把建筑空间作为长期数据资产来管理。

简单说：

  • 要一个好用的空间可视化组件，选 Smplrspace。
  • 要一套企业级空间数据底座，选 Archilogic。

两者不是完全替代关系。Smplrspace 更像“把空间展示和交互做好”；Archilogic 更像“把空间数据治理和系统集成做好”。选型时不要从“谁的 3D 更酷”开始，而应该从你的数据责任开始：这张平面图只是页面的一部分，还是未来所有空间业务的事实来源？
